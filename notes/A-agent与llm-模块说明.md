# agent.py + llm.py 模块说明（冯璐）

> 消化期交付物（10/19–10/20）　|　对应文件：`backend/app/agent.py`（504 行）、`backend/app/llm.py`（251 行）
> 用途：消化代码 + 技术文档第 4 章素材 + 答辩题库

---

## 一、这两个文件解决什么问题

**一句话**：把"用户的一句中文"安全地变成"一个可验证的最优排班方案"。

拆开是两件事：

- **`agent.py`** 负责**编排**。它定义了一条六步流水线，决定"先做什么、后做什么、每一步失败了怎么办"，并保证大模型只在**该出现的地方**出现。
- **`llm.py`** 负责**约束**。它把"调用大模型"这件事包成一个受控接口：输出必须符合 Pydantic schema，不符合就带着报错重试，网络异常就退避重试，Key 失效就抛中文人话错误。

**为什么要把它们分开**：编排是业务逻辑（会随需求变），模型调用是基础设施（基本不变）。混在一起的话，将来换模型厂商要动业务代码，改业务逻辑又可能碰坏重试逻辑。

## 二、数据从哪进来、到哪出去

```
用户中文 text: str
      │
      ▼
┌─────────────────────────────────────────────────────────┐
│ S1  understand()          ★ 大模型调用 ①                │
│     prompts.EXTRACTION_SYSTEM / _USER                    │
│     llm.chat_json(..., ExtractionResult)                 │
│     ├─ 兜底：source_text 为空则补原文（便于追溯）        │
│     └─ 规整：dates 排序去重（保证滑动窗口有意义）        │
└─────────────────────────────────────────────────────────┘
      │ ExtractionResult { problem, summary, uncertainties }
      ▼
┌─────────────────────────────────────────────────────────┐
│ S2  validate_problem() + repair_problem()     纯代码     │
│     校验 + 修补 LLM 抽出来的自相矛盾                     │
└─────────────────────────────────────────────────────────┘
      │ SchedulingProblem + list[str] warnings/repairs
      ▼
┌─────────────────────────────────────────────────────────┐
│ S3  数学建模（这一步没有独立函数，体现在 S4 的 _build）  │
└─────────────────────────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────────────────────────┐
│ S4  solve(problem, time_limit=15.0)           纯代码     │
│     asyncio.to_thread 包住，避免阻塞事件循环             │
└─────────────────────────────────────────────────────────┘
      │ SolveResult { status, assignments, conflicts, ... }
      ▼
┌─────────────────────────────────────────────────────────┐
│ S5  冲突诊断（结果已在 S4 内产生，这里只做状态映射）     │
│     result.conflicts → AgentStep.status = "warn"         │
└─────────────────────────────────────────────────────────┘
      │
      ├──► render_schedule_table() → schedule_table_md: str（给前端）
      ▼
┌─────────────────────────────────────────────────────────┐
│ S6  explain()             ★ 大模型调用 ②                │
│     fact_numbers() 先算好全部可引用数字                  │
│     llm.chat_text(..., NARRATIVE_USER)                   │
└─────────────────────────────────────────────────────────┘
      │ narrative: str
      ▼
┌─────────────────────────────────────────────────────────┐
│ number_guard(narrative, allowed_text)         纯代码     │
│ 返回「来源不明的数字」列表 → 非空则标 warn 并追加警告    │
└─────────────────────────────────────────────────────────┘
      │
      ▼
   AgentRun → 前端
```

**关键结论：整条链路 6 步，只有 S1 和 S6 进大模型，中间 4 步全是确定性代码。**

实测耗时也印证了这一点（同一道题跑 5 次）：S1 中位 4132 ms、S6 中位 2028 ms，而 S4 求解中位 **13 ms**。端到端 6178 ms 里，真正的计算只占 **0.21%**。

## 三、最关键的 3 个设计决策

### 决策一：用显式状态机，不用 ReAct 循环

**怎么做的**：`STEP_NAMES`（`agent.py:104`）把六步写死成常量，`run()`（`agent.py:228`）按固定顺序依次推进，每一步通过 `_find(steps, key)` 拿到对应的 `AgentStep` 并记录 `status` / `duration_ms` / `detail`。

**为什么这么选**：

1. **步骤本身是确定的**。排班这个问题，"识别需求 → 校验 → 建模 → 求解 → 诊断 → 解释"这个顺序不会因为输入不同而改变。让 ReAct 去"思考下一步做什么"，等于用不确定的机制去重新发现一个本来就确定的流程，只会引入随机性。
2. **每一步都能被前端可视化**。固定六步才能做那个"六步轨迹"面板，让评委一眼看到每步耗时——这恰好是"神经符号"最有说服力的展示。ReAct 的步骤数是动态的，画不出来。
3. **失败可以精确定位**。S1 挂了就是 Key/网络问题，S4 挂了就是建模问题，S6 挂了不影响方案。ReAct 循环里出问题，你只知道"某一轮错了"。

### 决策二：所有数字由后端算好，大模型只负责"说"

**怎么做的**：`fact_numbers()`（`agent.py:181`）在 S6 之前算出 10 个关键指标（总排班数、人均天数、最多/最少天数、求解耗时……），序列化成 JSON 塞进 prompt；同时这份 JSON 也是数字护栏白名单的一部分。

**为什么这么选**：大模型做算术不可靠，而且**错得很隐蔽**——把 28 个班次说成 35 个，人眼扫一遍根本发现不了，但在答辩现场被评委问一句就露馅。让它"引用"而不是"计算"，是从源头消灭这类错误。

### 决策三：`chat_json()` 用 schema 当契约，失败带着报错重试

**怎么做的**（`llm.py:178`）：`max_retries=1`，即最多 2 次。第一次解析失败时，把**模型自己的错误输出**以 `assistant` 角色、把**具体校验错误**以 `user` 角色追加进 messages，再请求一次。

**为什么这么选**：

1. **Pydantic schema 一份三用**——它就是 LLM 的输出格式说明、API 的接口契约、运行时的校验规则。改一处，三处同步，不会出现"文档说这样、代码收那样"。
2. **把错误喂回去比单纯重试有效得多**。模型看到"你上次漏了 `employees[2].max_shifts`，类型应为 int"之后，第二次命中率显著提高；盲目重试只是重复同一个错误。
3. **只重试 1 次是算过账的**。再失败说明 prompt 或 schema 有问题，继续重试只是烧钱拖时间，不如直接把原始输出片段抛给开发者看。

## 四、我还没搞懂的地方

> ⚠️ **这一节必须冯璐自己写，不许写"没有"。** 下面是三个候选，挑你真正没把握的改写成自己的话。

**候选 1：`number_guard()` 里 1–10 的白名单为什么是 10？**
`agent.py:77` 写的是 `{str(i) for i in range(1, 11)}`，代码没有注释说明这个 10 是怎么定的。我的推断是：中文决策说明里会大量出现"第一点""两步""三条建议"这类序数和通用量词，不放行会造成大面积误报；但 10 这个上界是否经过实测、换成 20 会不会漏掉真正的幻觉，我没验证过。

**候选 2：`repair_problem()` 修补之后，要不要告诉用户"我改了你的需求"？**
现在 `repairs` 会被塞进 `warnings` 一起返回。但如果修补的动作比较大（比如悄悄删掉了一个没人会的技能要求），只放在 warnings 里可能不够显眼。

**候选 3：S3「数学建模」这一步在代码里没有独立函数**
`run()` 里 S3 只是拼了一句 `detail` 文案（`agent.py:288`），真正的建模发生在 `solve()` 内部的 `_build()`。这样六步轨迹里 S3 的耗时恒为 0——展示上说得通（建模本来就是毫秒级），但严格讲这一"步"是虚的。要不要给它一个真实的计时？
