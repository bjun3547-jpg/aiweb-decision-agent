## 一、这个文件解决什么问题

`scheduling.py` 是项目里唯一「算得对」的地方：它用 OR-Tools 的 CP-SAT 求解器，把排班问题建成数学模型并**精确求解**。它做三件事：

1. 把五类业务规则（人数需求 / 不可用日期 / 天数上限 / 休息天数 / 连续工作）建成约束，求出**可验证的最优排班**；
2. 无解时不只报「无解」，而是定位到「哪几条规则互相冲突」，并生成**中文诊断**；
3. 把冲突规则转成带罚分的软约束重解，给出「**违约最小**」的近似方案供用户参考。

关键点：它**不感知大模型的存在**——输入是纯数据类，可以脱离 LLM 单独测试（`demo_scheduling.py` 就是证据）。

## 二、数据从哪进来、到哪出去

```
SchedulingProblem（schemas.py 的纯数据类，不含任何 LLM 痕迹）
        │
        ▼
validate_problem()  体检：把脏数据挡在建模之前
        │
        ▼
repair_problem()    确定性修补：兜住「班次要求技能却无人具备」这类自相矛盾
        │
        ▼
_build()            建 CP-SAT 模型：决策变量 x[e][d][s] → 约束 → 目标
        │
        ▼
solve()             三段式：硬约束求解 → 冲突诊断 → 软约束松弛
        │
        ▼
SolveResult          status / assignments(排班) / conflicts(冲突集) / violations / diagnosis
        │
        ▼
render_schedule_table()   渲染成 Markdown 排班表（前端与 CLI 共用）
```

## 三、最关键的 3 个设计决策 + 为什么

**决策 1：每类规则挂一个「假设字面量」，而不是每条约束挂一个。**
为什么：无解时能定位到「规则类别」（恒定 5 个），而不是几十条零散约束——后者对业务人员毫无意义；假设数量恒定，也让最小冲突集的搜索代价可接受。

**决策 2：用「删除法」把求解器的充分集收敛成最小集。**
为什么：`SufficientAssumptionsForInfeasibility()` 返回的是充分集，实测第一次跑 5 类规则**全部**被返回，等于没诊断。删除法逐条试删（删掉后仍无解就真删），剩下才是真正打架的那 2 条。

**决策 3：显式加「总人力成本」+「最小扰动」两个目标项。**
为什么：需求约束是「至少 N 人」的下界，不加成本项模型就没动力少排人——同一问题两次求解会给出 28 条 / 35 条，且都算"最优"。最小扰动项则让 what-if 只动 4 条，而不是整张表全部重排。

# 附：5 个验收问题自检答案

**Q1　决策变量是什么？「7 人 × 7 天 × 2 班次」有多少变量？**
决策变量 `x[e][d][s] ∈ {0,1}`，表示员工 e 在日期 d 是否上班次 s。7 × 7 × 2 = **98 个** x 变量；另有辅助变量 `w[e][d]`（每人每天是否上班）= 49 个。合计 **147 个布尔变量**（不含约束内部的临时变量）。

**Q2　五类规则对应什么业务含义？哪两类永不放宽、为什么？**
五类（可诊断、可松弛的业务规则）：
- `demand`：各班次人数满足需求
- `availability`：不可用日期不上班
- `max_shifts`：个人上班天数不超过上限
- `rest_days`：每 7 天最少休息 N 天
- `max_consecutive`：连续工作天数不超过上限

永不放宽的两类：**`skill_match`（技能匹配）** 和 **「每人每天最多一班」**。它们是**物理约束**——物理上不可能违反，不是业务取舍，松弛它们没有意义。

**Q3　无解时 `SufficientAssumptionsForInfeasibility()` 返回什么？**
返回「**充分集**」：通常是全部假设字面量（5 类规则全给），而且是**字面量在模型中的索引**（`BoolVar.Index()`），不是假设列表的下标。必须先建「索引 → 规则名」的反查表才能用。

**Q4　为什么还要用删除法再收敛一次？**
充分集没有信息量（"5 条规则都有问题" ≈ 没诊断）。删除法逐条试删：删掉某条后若**仍无解**，说明它非必需、就真删；剩下的是真正互相打架的**最小冲突集**（通常 2 条）。

**Q5　为什么必须显式加「总人力成本」目标项？不加会发生什么？**
需求约束写的是 `covered >= need`（至少 N 人，下界），模型没动力少排人 → 同一问题两次求解会给出 28 条 / 35 条，且都算"最优"。显式加 `sum(work) * 20` 让模型有动力少排人，结果才稳定在 28 条（README 5.2 记的就是这个真 bug）。
