# 把仓库推上 GitHub：两个叠加的环境坑

- **日期**：2026-10-17
- **参与人**：冯璐（及队友）
- **AI 工具 / 模型**：DeepSeek Harness（DeepSeek-V4-Flash）

## 1. 我的意图

第一次把本地仓库推上 GitHub，建成可给评审访问的公开仓库。

## 2. 我给的 Prompt

> 用 GitHub 创建

（最初选的是 Gitee，AI 建议先测网络再决定；测完之后我们改成了 GitHub。）

## 3. 遇到的两个坑

**坑一：`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`**

git 在 Windows 上默认用系统自带的 schannel 做 TLS，而这台机器上它直接失败。
换成本地排障时验证过：**curl 和 PowerShell 的 HTTPS 请求同样失败**，
但 Node 和 Python 的 HTTPS 正常 —— 说明不是网络问题，是 TLS 后端问题。

**坑二：`Recv failure: Connection was reset`**

修完坑一之后 push 依然失败。实测对比：

| 走法 | 结果 |
| --- | --- |
| 直连 github.com | **0/3 全失败** |
| 走本地代理 127.0.0.1:7897 | **3/3 全通** |

说明这台机器到 GitHub 的直连是被干扰的，必须走代理。

## 4. 我做了什么判断

**判断一：先量化，再决定。**

没有直接按"国内环境就用 Gitee"的惯性走，而是先测：GitHub 直连 0/3、Gitee 直连 3/3。
拿到数据后再决定平台，而不是凭感觉。

**判断二：两个坑要一起修，缺一不可。**

只修 TLS 后端会继续被网络重置挡住；只配代理会继续被 schannel 挡住。
我们逐项验证了四种组合，最终确认"openssl + 代理"才是通的。

**判断三：把配置固化进仓库，而不是留在命令行历史里。**

```
git config http.sslBackend openssl
git config http.proxy http://127.0.0.1:7897
```

这样队友拉下仓库后不用再踩一遍同样的坑。

**判断四：给评审视角做了一次自查。**

推完之后核了三件事：匿名能否读取（→ 公开性）、有没有密钥泄漏（→ 零命中）、
`.env` 有没有进仓库（→ 只有 `.env.example`）。
这三项是会被核查的，也是团队最容易忽略的。
