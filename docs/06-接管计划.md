# 接管计划：把「能跑的原型」变成「你们的作品」

> 编制日期：2026-10-17 晚　|　适用：冯璐 / 李芳青 / 郑茜文  
> 前置阅读：`00-作战方案.md`（时间线）、`05-分工实施计划.md`（角色分工）

---

## 0. 先定性：我们手上是什么

仓库里这份代码**能跑**——我实测过 `demo_scheduling.py`，最优排班和冲突自愈两个场景都正常输出，CP-SAT 求解 0.03 秒。

但它现在有一个尴尬的定位：

> **它是一个可用的原型底子，还不是「我们的作品」。**

区别在哪？评委不会只看它跑不跑，他们会问：

- 「这个冲突诊断是怎么定位到规则类别的？」——答不上来，作品就不算你的
- 「为什么不用 ReAct 而用状态机？」——答不上来，说明架构不是你选的
- 视频里要讲「AI 协同过程」，你讲不出自己代码的逻辑，这段就是空的
- 技术文档第 4、5 章要写「关键实现」，写不出来就是抄 README

**所以这 15 天真正的主线任务不是加功能，是「过手」。**

---

## 1. 三条原则

### ① 不推翻重写

15 天重写一个 CP-SAT 排班系统 + 冲突诊断 + what-if，做不出来。而且现在这套技术选型（神经-符号、显式状态机、类别级假设字面量）是**对的**，重写只会更差。

**要做的是：读懂它、改动它、讲清楚它。**

### ② 分头接管，一人一个文件

三个人同时读同一份 2860 行的代码，等于三个人都没读懂。

按「谁负责什么交付物，就接管哪个文件」来切——这样读代码和做交付物是同一件事，不是两件事。

### ③ 用「输出」倒逼「理解」

不要用「我今天读了 500 行」当进度。用**产出物**当进度：

- 写出一份能给别人讲的模块说明
- 回答出下面那 5 个问题
- 在自己的文件里做出一个真实的改动

读不懂就写不出来，写不出来就是没读懂。这是最快的自检方式。

## 3. 验收问题：答得出来才算接管完成

> 用法：先读代码，再合上代码回答。答不出来的那一条，就是你还没读懂的地方。  
> **这 15 个问题，就是技术文档第 4、5 章和答辩的题库。**

### 冯璐 —— `agent.py` + `llm.py`

1. **六个步骤**分别是什么？每一步的输入和输出各是什么类型？
2. 为什么用**显式状态机**而不是 ReAct 循环？说出至少两个具体理由。
3. `number_guard()` 怎么判断一个数字「来源不明」？它为什么要把 1–10 放进白名单？
4. LLM 返回的 JSON 不符合 schema 时，`chat_json()` 具体做了什么？（提示：它重试了几次、把什么喂回去了）
5. what-if 里为什么要**先把原问题也重算一遍** `baseline`，而不是直接拿上次的结果？

### 李芳青 —— `static/index.html`

1. 页面一共几个区块？每个区块的数据分别来自后端返回的哪个字段？
2. `submit()` 里从点击到出结果，完整经过哪几步？出错时错误信息显示在哪？
3. `schedule_table_md` 是一段 Markdown 文本，前端是怎么把它变成排班表格的？
4. 六步轨迹有 `ok / warn / error / running` 几种状态，界面上分别怎么表现？
5. 如果现在要加一个「工时热力图」，你会改哪几行？数据从哪取？

### 郑茜文 —— `solver/scheduling.py`

1. **决策变量**是什么？一个「7 人 × 7 天 × 2 班次」的问题有多少个变量？
2. 五类规则分别对应什么业务含义？哪两类**永不放宽**，为什么？
3. 无解时，`SufficientAssumptionsForInfeasibility()` 返回的是**什么**？（这个坑很多人踩）
4. 既然已经有上面的返回值，为什么还要用「删除法」再收敛一次？它解决什么问题？
5. 为什么必须显式加一个「总人力成本」目标项？不加会发生什么？（提示：README 5.2 记的那个真 bug）

### 10/18 下午：读自己那份（第一遍）

不求全懂。目标只有一个：**能画出这个文件的流程图**（手画也行，拍照发群里）。

### 10/19 – 10/20：写「我的模块说明」+ 回答 5 个问题

每人交一份 **800 字左右**的说明，包含：

1. 这个文件解决什么问题
2. 数据从哪进来、到哪出去（画个箭头图）
3. 最关键的 3 个设计决策，以及**为什么这么选**
4. 我还没搞懂的地方（**必须写，不许写"没有"**）

> 这份说明有三个用途：消化代码的方式、技术文档的素材、一次真实的 Git 提交。  
> 一石三鸟，别偷懒。

**提交信息格式：**

```
docs: 冯璐 - agent.py 模块说明
docs: 李芳青 - 前端页面结构说明
docs: 郑茜文 - 求解器模块说明
```

## 7. Git 历史怎么处理

**现状**：17 条提交，全部由冯璐一人完成，全部在 10/17 一天内。

**不要做的事**：用 `git commit --date` 伪造时间。那是作弊，而且 `git reflog` 一查就露，比现在的状态更糟。

**要做的事**：从 10/18 起，三个人真实地、每天地提交。到 11/01 时会有约 40–50 条提交、跨 15 天、三个作者——那时最初的「一天 17 条」自然会被解释成「第一天搭原型」，是合理的。

**换句话说：这个问题只能靠后面的真实工作盖过去，不能靠补历史。**

---

## 8. 现在最该警惕的三件事

1. **讲不出来 = 不是你们的作品。** 这是当前第一风险，比 Git 历史更致命，因为它会在答辩现场暴露。
2. **别为了「看起来是自己做的」去改架构。** 现在这套设计是对的，改坏了没时间修。要改就改小的、能测的。
3. **消化期别省。** 三个人花 3 天读透自己的文件，换回来的是文档第 4、5 章、视频的机制讲解、答辩的底气。这是这 15 天里性价比最高的 3 天。
