### 4.2 选型理由（2 页）★

**写什么**：四个选型，每个都要写"考虑过什么、为什么没选"

**① 为什么用 LLM，而不是规则模板 / 意图分类模型**

- 规则模板：排班需求的说法太多（"每人最多上5天" / "不能连上超过5天" / "周休两天"），模板写不完
- 意图分类：只能识别"这是排班问题"，抽不出具体参数
- LLM 的优势：把任意中文说法映射到固定 schema，且能处理隐含信息（"张伟周三有事" → 不可用日期）

**② 为什么用显式状态机，而不是 ReAct / AutoGPT 式自主循环**

| 对比项 | ReAct 自主循环 | 显式状态机（我们） |
| --- | --- | --- |
| 步骤可预测 | 否，每次路径可能不同 | 是，固定六步 |
| 输出可校验 | 难，中间结果格式不定 | 是，每步 JSON Schema 卡死 |
| 失败可回退 | 难 | 是，可退回上一步 |
| 可评测 | 难 | 是，每步可单独测 |

**关键论点**：运筹建模的步骤本身就是确定的（识别 → 定变量 → 定目标 → 定约束 → 求解），**不需要 Agent 自己摸索**。用自主循环是"为了显得智能而牺牲可靠性"。

**③ 为什么用 CP-SAT，而不是线性规划 / 启发式 / 让 LLM 直接排**

| 方案 | 为什么不选 |
| --- | --- |
| 线性规划 (LP) | 排班是 0/1 决策 + 逻辑约束（"要么…要么…"），LP 表达不了 |
| 启发式/遗传算法 | 只能给"较好的解"，无法证明最优，也无法给出冲突集 |
| 让 LLM 直接排 | 会漏需求、超工时，且**无法验证**——这是本项目要解决的核心问题 |
| **CP-SAT** | 原生支持布尔变量和逻辑约束，能证明最优，**且支持假设集做冲突诊断**（这是关键，LP 没有对应能力） |

**④ 为什么用 DeepSeek，而不是 GPT-4 / 本地模型**

- 中文语义理解好，成本低（学生队可承受）
- 支持 `response_format: json_object`，结构化输出稳定
- **封装成 OpenAI 兼容适配层**：换模型只改 `base_url` + `model` 两个环境变量，不动上层代码

**必须放**：表 5 —— 四个选型对比汇总

### 4.3 集成方式（2 页）★

**写什么**：AI 是怎么"接进"系统的，给出完整数据流

**必须放**：图 4 —— 数据流图

```
中文需求
  → [LLM] ExtractionResult (Pydantic 强校验)
  → [确定性代码] repair_problem() 修补矛盾
  → SchedulingProblem (纯数据结构，不含任何 LLM 痕迹)
  → [CP-SAT] SolveResult
  → [后端算好事实数字] fact_numbers()
  → [LLM] 自然语言决策说明
  → [数字护栏] 校验说明里的数字
```

**三个集成要点，每点配一段代码（10 行以内）**：

1. **接口隔离**：`SchedulingProblem` 是纯数据类，求解器完全不感知 LLM 的存在。这意味着**求解器可以脱离 LLM 单独测试**（`/api/solver/solve` 接口就是证据）。
2. **Schema 即契约**：`schemas.py` 里的 Pydantic 模型既是 LLM 的输出格式，也是前后端的接口格式，还是校验规则——一份定义三处复用。
3. **单向依赖**：LLM 层依赖 schemas，求解器层依赖 schemas，但两层互不依赖。所以换模型不影响求解，改求解不影响提示词。

### 4.4 优化策略（1 页）★

**写什么**：官方要的"优化策略"，指的是**你们为了让 AI 输出可靠做了哪些工程手段**。列成表最清楚：

**必须放**：表 6 —— 六项优化策略

| # | 策略 | 解决什么问题 | 效果 |
| --- | --- | --- | --- |
| 1 | 结构化输出 + 校验失败回灌重试 | LLM 输出格式漂移 | 字段缺失/类型错误被拦在建模之前 |
| 2 | temperature = 0.1 | 同一输入结果不稳定 | 抽取结果基本可复现 |

### 5.2 排班数学模型（1.5 页）

**必须放**：公式块（用 Word 公式编辑器，不要贴图片）

- 决策变量：$x_{e,d,s} \in \{0,1\}$（员工 e 在日期 d 是否上班次 s）
- 目标：$\min \; 20\sum w_{e,d} + 15\cdot\Delta_{\text{stab}} + 10(\max_e L_e - \min_e L_e) + 3\sum \text{pref}$
- 五类约束：需求、不可用、天数上限、休息天数、连续工作

**写什么**：每个符号解释一句；说明为什么这样定权重（20 > 15 > 10 > 3 的优先级含义）。

### 5.3 不可行自愈的两个难点（2 页）★

**必须写清楚这两个坑**（素材在 `docs/prompts/2026-10-17-02-求解器与不可行自愈.md`）：

**难点一**：`SufficientAssumptionsForInfeasibility()` 返回的是**字面量在模型中的索引**，不是假设列表的下标。必须先建 `BoolVar.Index() → 规则名` 的反查表。

**难点二**：它返回的是「**充分集**」不是「**最小集**」。实测第一次跑，5 类规则**全部**返回——对业务方等于没说。

**我们的解法**：删除法（delta-debugging）

```
for 每条规则 r:
    如果去掉 r 之后仍然无解:
        真的去掉 r
剩下的就是最小冲突集
```

因为假设粒度是"每类规则一个"，总量恒定为 5 个，所以搜索代价可接受（5 次求解，每次 < 0.1 秒）。

**必须放**：图 6 —— 一个真实的诊断输出截图（"42 人班 vs 34 人班，缺口 8"那段）

### 5.4 最小扰动重排（1.5 页）

**写什么**：**讲清楚两个先后发现的 bug**

**Bug 1**：需求约束写成 `已排人数 >= 需求人数`（下界），模型没有动力少排人。同一问题两次求解分别给出 28 条和 35 条，**且都算"最优"**。修法：加总人力成本项。

**Bug 2**：修完之后，单个人少上一天，整张表 28 条全变。业务上不可接受。修法：传入 baseline，对"与原方案不同"的分配记惩罚分。

| --- | --- | --- |

| 修复后 | 恒为 28 | **4 / 28** |
