## 3.1 分层架构

### 3.1.1 整体结构

系统分为五层，自上而下依次是交互层、接口层、编排层、能力层与护栏层。

```
┌─────────────────────────────────────────────────────────────┐
│  ① 交互层   backend/app/static/index.html（978 行）          │
│     Vue 3 全局构建 · 单文件 · 零构建步骤                      │
│     职责：把自然语言送上去，把 JSON 画成排班表                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST / JSON
┌───────────────────────────▼─────────────────────────────────┐
│  ② 接口层   backend/app/main.py（FastAPI）                    │
│     /api/agent/run · /api/agent/whatif · /api/solver/solve    │
│     /api/health（含模型余额探测）                              │
│     职责：路由、CORS、静态托管、异常转 HTTP 语义               │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  ③ 编排层   backend/app/agent.py（六步显式状态机）            │
│     理解需求 → 数据校验 → 数学建模 → 精确求解 → 冲突诊断 →     │
│     生成决策说明                                              │
│     职责：决定"下一步做什么"，不负责"具体怎么算"                │
└──────────┬──────────────────────────────┬───────────────────┘
           │ 只要 JSON                     │ 只要数据类
┌──────────▼──────────────┐  ┌────────────▼───────────────────┐
│ ④a 语言能力  llm.py      │  │ ④b 计算能力 solver/scheduling.py│
│    仅依赖 httpx          │  │    OR-Tools CP-SAT 9.15         │
│    自然语言 ⇄ JSON       │  │    771 行，纯函数，无 IO        │
│    不知道"排班"是什么     │  │    不知道"大模型"存在           │
└──────────┬──────────────┘  └────────────┬───────────────────┘
           │                              │
┌──────────▼──────────────────────────────▼───────────────────┐
│  ⑤ 护栏层   三道闸门，拦住大模型幻觉污染数学模型                │
│     结构护栏 chat_json()   → schema 不符就带着报错重试         │
│     语义护栏 repair_problem() → 自相矛盾自动修补               │
│     数字护栏 number_guard()  → 说明里出现来源不明的数字就标记   │
└─────────────────────────────────────────────────────────────┘

              ┌──────────────────────────────┐
              │ 贯穿全局：schemas.py          │
              │ Pydantic 数据模型 = 层间契约   │
              │ 同时充当 LLM 的 JSON Schema    │
              └──────────────────────────────┘
```

### 3.1.2 每层的职责边界

| 层 | 职责（一句话） | 明确不做什么 |
| --- | --- | --- |
| ① 交互层 | 收集输入、渲染结果 | 不做任何业务判断，不校验约束 |
| ② 接口层 | 协议转换、静态托管 | 不写业务逻辑 |
| ③ 编排层 | 决定步骤顺序、记录轨迹、汇总结果 | 不调用模型 API，不建模求解 |
| ④a 语言层 | 自然语言与 JSON 互译 | 不做任何计算 |
| ④b 计算层 | 建模与精确求解 | 不解析自然语言，不生成文案 |
| ⑤ 护栏层 | 拦截结构、语义、数字三类错误 | 不参与正常路径的性能开销 |

### 3.1.3 为什么这样分层

分层的直接动机不是"看起来规范"，而是**三处真实的可替换性**：

**第一，换大模型不影响求解器。**
`llm.py` 全文只依赖 `httpx` 和 `pydantic` 两个第三方库，走 OpenAI 兼容协议。
模型名、`base_url`、超时、温度全部来自环境变量，切换模型只改 `.env`，
`solver/` 目录一行不用动。

**第二，换求解器不影响交互。**
`solver/scheduling.py` 的入口是 `solve(problem: SchedulingProblem, ...) -> SolveResult`，
输入输出都是 `schemas.py` 里的纯数据类，函数内部没有任何网络、文件、模型调用。
它完全可以脱离整个项目单独测试——`backend/demo_scheduling.py` 就是这么做的。

**第三，换前端不影响后端。**
前后端之间只有 REST 契约，前端不认识 `SchedulingProblem` 之外的东西。
这让我们能在 15 天的周期里用"单文件 + 零构建"的前端，而不必担心它成为架构负担。

### 3.1.4 一条贯穿全局的边界：谁计算，谁说话

整个架构只有一条硬边界，其余都是它的推论：

> **所有数字由确定性代码产生，大模型只负责"把话翻译成结构"和"把结构翻译回话"。**

这条边界在代码里能被指出来：

| 位置 | 表现 |
| --- | --- |
| `agent.py` 的 `fact_numbers()` | 先算出 10 个关键指标，再喂给模型写说明 |
| `agent.py` 的 `_date_anchors()` | "本周/下周"的边界日期由 Python 算好，模型只准照抄 |
| `agent.py` 的 `number_guard()` | 说明里出现白名单外的数字，直接标记为可疑 |
| `agent.py` 的 what-if | 原方案的 `baseline` 由后端重算，不信任前端缓存 |

这条边界的代价是"少了一点灵活"，收益是**结果可验证、可复现、可审计**。
对一个要给店长看的排班系统来说，这个交换是划算的。

### 3.1.5 一次请求的完整数据流

以 7 人便利店场景为例，一次 `/api/agent/run` 的真实耗时分布：

| 阶段 | 层 | 耗时 | 占比 | 产出 |
| --- | --- | --- | --- | --- |
| S1 理解需求 | ③ → ④a | 4149 ms | 62.6% | `ExtractionResult`（含 `SchedulingProblem`） |
| S2 数据校验 | ③ | < 1 ms | — | 警告列表 |
| S3 数学建模 | ③ | < 1 ms | — | 决策变量约 98 个 |
| S4 精确求解 | ③ → ④b | **29 ms** | **0.44%** | `SolveResult`，28 条排班，OPTIMAL |
| S5 冲突诊断 | ③ | 0 ms | — | 约束可满足，无需松弛 |
| S6 生成决策说明 | ③ → ④a | 2362 ms | 35.7% | 中文决策说明 |
| **合计** | | **6625 ms** | 100% | |

**这张表是整章最重要的证据**：真正决定方案质量的计算只花 29 毫秒，
**99.5% 的时间不花在求解上**——其中两次语言转换占 98.3%，其余是步骤间开销。
这说明系统的瓶颈在"理解"和"表达"，而不在"求解"，后续优化的方向也因此很清楚。

## 3.2 关键设计决策

架构上的每一个选择都意味着放弃另一些可能性。本节记录三个最关键的取舍。

### 表 3　三个关键设计决策

| 决策点 | 我们的选择 | 为什么 | 放弃了什么 | 什么时候会后悔 |
| --- | --- | --- | --- | --- |
| 编排方式 | **显式状态机**（六步固定） | 步骤确定、每步可校验、出错能定位到具体一步、可逐阶段评测 | ReAct 的开放式探索能力 | 遇到需要"边想边找工具"的开放式任务时 |
| 计算方式 | **CP-SAT 精确求解** | 结果可验证、同输入同输出、无解时能说出冲突 | "让模型直接生成方案"的简单做法 | 问题规模大到精确求解不可行时（本项目未触及） |
| 前端形态 | **Vue 3 单文件 + 内置运行时** | 零构建、离线可跑、评委 clone 下来直接开 | 工程化构建带来的模块化与生态 | 页面规模超过 2000 行时 |

### 3.2.1 为什么是状态机而不是 ReAct

ReAct（Reasoning + Acting）是当前 Agent 的主流范式：让模型自己决定下一步调用什么工具、调用几次。
它适合**开放式探索任务**——比如"帮我查一下这个行业最近的融资情况"，路径无法预先确定。

而排班是一个**封闭式决策任务**：从一句话到一张排班表，中间必经的步骤是固定的，
不存在"要不要先查个天气"这种分支。在这种情况下，ReAct 带来的是纯粹的成本：

1. **不可预测的调用次数**。ReAct 的每一轮都要一次模型调用，一个 6 步任务可能跑成 4 轮也可能跑成 11 轮，
   耗时和费用无法预估。而状态机固定 2 次模型调用（S1 和 S6），端到端耗时稳定在 6–7 秒。
2. **错误定位困难**。状态机里 S4 挂了，一定是用例或建模的问题；ReAct 里出错，
   你只知道"某一轮推理偏了"，排查成本高一个数量级。
3. **无法逐阶段评测**。我们需要知道"是理解错了，还是算错了"。
   状态机每一步都有独立的输入输出和耗时，可以直接拿来评测；ReAct 的中间态是一段自然语言推理，无法结构化断言。

**这条决策的代价是**：系统不能处理"用户一句话里包含多个不相关诉求"的情况。
我们接受了这个限制——排班场景里它很少发生。

### 3.2.2 为什么是精确求解而不是让模型直接排

最省事的做法是把员工名单和规则丢给大模型，让它直接输出一张排班表。
我们在早期验证阶段试过这条路，它在三个方面不可接受：

1. **约束满足不可验证**。模型给出的表看起来合理，但你无法证明它满足"每人每周最多 5 天"。
   而 CP-SAT 给出的解带 `OPTIMAL` 状态，是可以逐条核对的。
2. **同输入不同输出**。同一个需求跑两次，模型可能给出两张不同的表。排班是管理行为，
   店长需要的是"可复现的决策"，不是"每次都有新惊喜"。
3. **无解时无法解释**。模型遇到排不出来的情况，通常会给一个"差不多"的方案并声称可行。
   而 CP-SAT 会返回 `INFEASIBLE`，并且我们能用删除法定位到**哪两条规则在打架**。

**这条决策的代价是**：必须把自然语言需求翻译成结构化的数学模型，这一步本身就会引入错误——
所以才有第五层护栏的存在。换句话说，**护栏是为这个决策付出的代价，也是它的配套**。

### 3.2.3 为什么前端不用构建工具

前端是一个 978 行的单文件，Vue 3 通过 `<script>` 直接引入仓库内的 `vendor/vue.global.prod.js`，
没有 `package.json`、没有 `node_modules`、没有构建产物。（10 月中旬做了一轮体验加固——加载骨架屏、
错误分类提示、工时均衡度卡片——行数从 561 涨到 978，但「单文件 + 零构建」这个结构没有变。）

这不是"图省事"，而是针对**交付场景**的判断：评委拿到仓库后需要能当场跑起来。
一旦引入构建工具，就多出三类失败可能——`npm install` 网络失败、Node 版本不匹配、
构建产物没提交。而现在的前端是"打开页面就能用"，由 FastAPI 的 `StaticFiles` 直接托管。

**这条决策的代价是**：样式、模板、逻辑全在一个文件里，改起来要找。
我们判断这个代价在 15 天周期内是可接受的，事实也是如此——这个文件自首次提交后只改过两次
（加 what-if 对比视图、修一处示例文本的 bug）。

### 3.2.4 我们考虑过但没有选的方案

| 方案 | 为什么没选 |
| --- | --- |
| LangChain / LlamaIndex 等 Agent 框架 | 我们的流程是固定的六步，框架提供的灵活性用不上，反而增加一层黑盒 |
| 微调一个专用小模型做需求抽取 | 训练数据不足（我们没有真实的排班需求语料），且微调后仍无法保证 schema 合规 |
| 前端用 React + Vite | 构建链带来的交付风险大于它带来的开发便利 |
| 把求解器换成启发式算法（遗传/贪心） | 启发式无法给出"最优"证明，也无法在无解时定位冲突 |

## 本章小结

本章的核心论点是：**这个系统的架构，本质上是"把语言能力和计算能力分开"这一条判断的展开。**

- 分层是为了让两种能力可以各自替换、各自测试；
- 状态机是为了让"什么时候用语言、什么时候用计算"变成显式规则，而不是模型的自由发挥；
- 精确求解是为了让计算结果可验证；
- 三道护栏是为了给"语言转结构"这一步兜底。

第 4 章将展开这条判断在 AI 技术层面的具体实现：为什么选这个模型、怎么集成、怎么优化。
