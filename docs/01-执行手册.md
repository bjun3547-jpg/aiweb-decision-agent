## 0. 三条原则（先读这个，比任务卡重要）

### ① 不推翻重写

15 天重写一个 CP-SAT 排班系统 + 冲突诊断 + what-if，做不出来。而且现在这套技术选型（神经-符号、显式状态机、类别级假设字面量）是**对的**，重写只会更差。

**要做的是：读懂它、改动它、讲清楚它。**

### ② 分头接管，一人一个文件

三个人同时读同一份 2860 行的代码，等于三个人都没读懂。
按「谁负责什么交付物，就接管哪个文件」切——这样读代码和做交付物是同一件事。

### ③ 用「输出」倒逼「理解」

不要用「我今天读了 500 行」当进度，用**产出物**当进度：一份能讲清的模块说明、答得出 15 个验收问题、在自己文件里做出一个真实改动。

> **读不懂就写不出来，写不出来就是没读懂。** 这是最快的自检方式。

## 四、Git 协作约定

### 2.1 分支策略：**不建分支，直接在 main 上改**

**理由**（不是图省事，是算过账）：

- 三个人改**不同的文件**，冲突概率接近零，分支带来的隔离收益很小
- 分支 + PR 的价值在"代码评审"，而你们没有第四个人来评审
- 你们的工期 15 天，多出来的操作步骤只会增加出错面

**但有三条替代规则，比分支更重要：**

| 规则 | 具体做法 |
| --- | --- |
| ① `main` 必须始终能跑 | **push 之前必须先跑一遍**：`..\.venv\Scripts\python.exe demo_scheduling.py` 要能出两个结果 |
| ② 小步提交 | 改完一小块就提交，别攒一整天 |
| ③ 动手前先 pull | 每天早上和每次动手前各 `git pull` 一次 |

**唯一需要建分支的情况**：有人要做**风险较高的试验**（比如把前端整个重构），
这时建个分支随便折腾，成功了再合并，失败了直接删掉，`main` 不受影响。

```powershell
git switch -c experiment           # 建分支试验
# ... 随便改 ...
git switch main                    # 放弃，回到 main
git branch -D experiment           # 删掉分支，什么都没发生
```

### 2.2 提交信息规范

```
<类型>: <做了什么>
```

| 类型 | 什么时候用 |
| --- | --- |
| `feat` | 加了新功能 |
| `fix` | 修了 bug |
| `docs` | 只改文档 |
| `chore` | 环境、依赖、配置 |
| `refactor` | 重构（功能没变） |

**好例子 / 坏例子：**

| | |
| --- | --- |
| ✅ `feat: 排班表增加工时热力图` | 一眼知道做了什么 |
| ✅ `fix: 冲突诊断在 1 人场景下报错` | 一眼知道修了什么 |
| ❌ `更新` | 等于没写 |
| ❌ `最终版` | 后面还会有"最终版2" |

### 2.3 每天固定动作

**早上第一件事（30 秒）：**

```powershell
cd F:\AIWeb
git pull
```

**晚上最后一件事（30 秒）：**

```powershell
cd F:\AIWeb
..\.venv\Scripts\python.exe backend\demo_scheduling.py    # 自检：能跑吗？
git add .
git commit -m "feat: 今天做了什么"
git pull
git push
```

### 2.4 出错怎么办

| 现象 | 含义 | 解决 |
| --- | --- | --- |
| `! [rejected] main -> main (fetch first)` | 队友比你先推了 | `git pull --rebase` 然后 `git push` |
| `CONFLICT (content): Merge conflict in xxx` | 两人改了同一行 | **立刻群里喊人**，不要自己乱选 |
| `error: Your local changes would be overwritten` | 你有没提交的改动，pull 不下来 | 先 `git stash`，pull 完再 `git stash pop` |
| 完全乱了，想推倒重来 | — | `git checkout .` 丢弃本地改动（**会丢代码，先确认**） |

## 十三、Git 历史怎么处理

**现状**：10/17 一天内、由冯璐一人完成了全部提交。

**绝对不要做的事**：用 `git commit --date` 伪造时间。那是作弊，`git reflog` 一查就露，比现在的状态更糟。

**要做的事**：从 10/18 起，三个人真实地、每天地提交。到 11/01 会有约 40–50 条提交、跨 15 天、三个作者——那时最初的「一天十几条」自然会被解释成「第一天搭原型」，完全合理。

> **这个问题只能靠后续的真实工作盖过去，不能靠补历史。**

---

## 十四、现在最该警惕的三件事

1. **讲不出来 = 不是你们的作品。** 这是当前第一风险，比 Git 历史更致命，因为它会在答辩现场暴露。
2. **别为了「看起来是自己做的」去改架构。** 现在这套设计是对的，改坏了没时间修。要改就改小的、能测的。
3. **消化期别省。** 三个人花 3 天读透自己的文件，换回来的是文档第 4、5 章、视频的机制讲解、答辩的底气。这是 15 天里性价比最高的 3 天。
